# Signed updates

Sonar updates its kernel from GitHub Releases of `pronzzz/sonar`. A
release is a kernel image plus a manifest signed with an Ed25519 key; the
matching public key is compiled into every kernel, and nothing that fails
the signature or the SHA-256 is installed or booted.

```
sonar:/$ update check
update: checking github.com/pronzzz/sonar
update: Sonar 0.1.1 is available (this is 0.1.0), release v0.1.1
  signed manifest verified: sonar-0.1.1-Image, 499712 bytes, sha256 d9f1...
  run 'update install' to install it
sonar:/$ update install
update: downloading sonar-0.1.1-Image (488 KiB)
update: signature and SHA-256 verified (d9f117305c2952ab...), 28 ms
update: installed Sonar 0.1.1 as /boot/kernel (the previous one is kept as /boot/kernel.prev)
update: restart to use it. ...
```

| Command | |
| --- | --- |
| `update check` | is there a newer signed release? (the default) |
| `update install` | download, verify and install it; `--force` also reinstalls an equal or older version |
| `update status` | what is running, what is installed, where updates come from |
| `update rollback` | swap `/boot/kernel` and `/boot/kernel.prev` |
| `update clear` | move `/boot/kernel` aside, so the built-in kernel starts |
| `update verify FILE [IMAGE]` | check a manifest or a `/boot/kernel` bundle on disk |
| `sha256 FILE...` | print checksums |

Settings, with `config KEY VALUE` (`none` unsets one):

| Key | |
| --- | --- |
| `update.auto` | `off` (default); `check`: say at boot when an update is available; `install`: also install it (it takes effect at the next start) |
| `update.repo` | GitHub repository, default `pronzzz/sonar` |
| `update.token` | GitHub token, only for a private repository (see below) |
| `update.api` | GitHub API base URL, default `https://api.github.com` |
| `update.mirror` | base URL of another server holding `sonar-update.txt` and the image, instead of GitHub |

## The repository must be public

Devices download without credentials, and GitHub answers requests for a
private repository's releases with 404. While `pronzzz/sonar` is private,
`update check` says so:

```
update: nothing at https://api.github.com/repos/pronzzz/sonar/releases/latest (HTTP 404).
  If github.com/pronzzz/sonar is private, devices cannot see its releases: make the
  repository public, or give this computer a read-only token with
  'config update.token TOKEN' (see docs/updates.md).
```

So for devices to update, either make the repository public, or give each
device a token: a fine-grained personal access token limited to this one
repository with read-only **Contents** permission, set with `config
update.token github_pat_...`. Be aware that the token is stored in plain
text in `/etc/sonar.conf`, and that Sonar's TLS does not authenticate
servers (below), so an attacker who can intercept the device's traffic can
capture the token. A public repository needs no token and has no such
risk. Until then, `update.mirror` or `tools/update_server.py` (below) serve
releases from a local machine.

## Making a release

1. Bump `OS_VERSION` in `kernel/include/kernel.h` and commit.
2. Either push a tag `vX.Y.Z` matching it: the workflow
   [`.github/workflows/release.yml`](../.github/workflows/release.yml)
   builds the kernel, signs it with the `SONAR_UPDATE_SIGNING_KEY` secret
   and publishes the release; or run `tools/release.sh --publish` on a
   machine with the key and `gh`, which does the same.

`tools/release.sh` without `--publish` only builds `dist/vX.Y.Z/`:

| File | |
| --- | --- |
| `sonar-X.Y.Z-Image` | the kernel (`build/Image`: a Linux arm64 Image and a UEFI application) |
| `sonar-update.txt` | the signed manifest |
| `SHA256SUMS` | checksums of both, for people |

It refuses to sign with a key other than the one in
`kernel/update/update_key.h`, since devices would reject the release.

### The signing key

The private key is 32 random bytes (an Ed25519 seed) in hex. It exists in
two places only: the repository's Actions secret `SONAR_UPDATE_SIGNING_KEY`
and, outside the repository, `~/.config/sonar/update_signing_key` (mode
600) on the maintainer's computer. It is never committed. The public key
is `kernel/update/update_key.h`, generated by `tools/sonar_update.py
header`.

```
python3 tools/sonar_update.py keygen                 # new key (refuses to overwrite)
python3 tools/sonar_update.py pubkey                 # its public key
python3 tools/sonar_update.py header > kernel/update/update_key.h
gh secret set SONAR_UPDATE_SIGNING_KEY -R pronzzz/sonar < ~/.config/sonar/update_signing_key
```

To change the key, ship a release signed with the old key whose kernel
contains the new public key; kernels only trust the key they were built
with. If the private key is lost, installed systems can no longer be
updated over the network (they can still be reinstalled from a disk
image). If it leaks, anyone can sign updates: rotate as above at once.

## Formats

`sonar-update.txt`:

```
sonar-update 1
version 0.1.1
arch aarch64
file sonar-0.1.1-Image
size 499712
sha256 d9f117305c2952ab...
key 49758b6872ed1f21
ed25519 <128 hex digits>
```

The last line is an Ed25519 signature (RFC 8032) of every byte before it.
The kernel checks the signature before it reads any field, then the
image's size and SHA-256, and that the image has the PE (`MZ`) and arm64
Image (`ARM\x64`) headers. `key` is the start of the public key, for
people. Signing and checking on the host: `tools/sonar_update.py
manifest|verify` (plain Python, no dependencies).

`/boot/kernel` on the system disk is a bundle: `SONARUPD`, the manifest's
length (u32, little-endian), 4 zero bytes, the manifest, zeros up to byte
4096, then the image. `/boot/ok` holds the SHA-256 (hex) of the last
update that started successfully.

Only a newer version is installed (`--force` overrides) and only a newer
version than the built-in kernel is booted, so an old signed release
cannot be replayed to downgrade a device.

## Downloading from GitHub: TLS without certificate checks

GitHub serves everything over HTTPS only: the API and release downloads,
which redirect to `objects.githubusercontent.com` or
`release-assets.githubusercontent.com`. Sonar therefore has a TLS 1.3
client (`kernel/net/tls.c`), built on its own crypto (`kernel/crypto`:
SHA-256/512, HMAC, HKDF, X25519, ChaCha20-Poly1305, Ed25519, checked by
`make test-crypto` against vectors from OpenSSL). It offers exactly one
cipher suite, `TLS_CHACHA20_POLY1305_SHA256` with X25519, which all of
GitHub's hosts accept, and it is constant time in software.

**It does not verify the server's certificate chain or its
CertificateVerify signature.** Doing so means X.509 parsing, RSA and ECDSA
P-256/P-384, a root certificate store and a trusted clock, which Sonar
does not have. TLS here protects against eavesdropping only: an active
attacker on the network path can pretend to be GitHub. That is acceptable
for updates because the trust comes from the signature, not the
connection: such an attacker can serve an old manifest (refused, it is
not newer), a tampered one (refused, bad signature) or nothing (no
update), but cannot get a kernel installed or booted. It is not
acceptable for secrets, which is why the token caveat above matters, and
why `fetch https://...` warns that the server is not authenticated.

The download path, with no token, is two requests to `api.github.com`
(`/repos/OWNER/REPO/releases/latest`, then each asset with `Accept:
application/octet-stream`), each answered with a redirect to GitHub's
download host. A token is sent only on the first request of each, never
after a redirect.

## Getting the new kernel onto the boot path

UEFI firmware starts `\EFI\BOOT\BOOTAA64.EFI` from the FAT32 EFI
partition. Sonar has no FAT driver, and there were two ways to get a new
kernel booted:

1. a minimal FAT32 writer that overwrites `BOOTAA64.EFI` in place, or
2. the kernel on the EFI partition, in its UEFI loader stub, preferring a
   kernel stored on the SonarFS system partition.

Sonar does **2**. Overwriting the only bootable file in place cannot be
made safe against a power cut (FAT has no journal; a half-written
`BOOTAA64.EFI` is an unbootable computer), it only works while the new
kernel fits the old file's clusters, and it leaves no fallback. With 2,
the kernel on the EFI partition is never modified by the updater and is
always there to fall back to; the new kernel is written through SonarFS,
whose journal keeps its metadata consistent; and the loader verifies the
signature and hash again at every boot, so a corrupted or tampered file
is never started.

At every UEFI boot, `efi_update.c`, called first thing by `efi_main`:

1. finds a SonarFS volume through the firmware's Block I/O protocol and
   reads `/boot/kernel` with a small read-only SonarFS reader (if the
   volume's journal holds an unapplied transaction it does nothing; the
   kernel replays it at mount);
2. verifies it (`bundle_verify`, shared with the kernel), and uses it only
   if its version is newer than its own;
3. unless `/boot/ok` holds the update's hash, counts the attempt in a UEFI
   variable (`SonarUpdateTries`); after 3 starts that never got as far
   as the network stage of boot, it skips the update;
4. starts it with `LoadImage`/`StartImage`, handing over its boot drive
   (for `board.dtb`, `system.img`, the model) and the load option
   `sonar.chained <sha256>`, so the update's own stub does not chain
   again.

Anything unexpected (no volume, a bad file, an older version, a failed
start) means the built-in kernel boots, and says why: `update status`
shows the loader's note. The update, once its file system and network
are up, writes its hash to `/boot/ok`. `update install` keeps the
previous update as `/boot/kernel.prev`; `update rollback` and `update
clear` choose between them and the built-in kernel.

Limitations of this design:

- **UEFI only.** QEMU `-kernel` (`make run`) and other loaders that load
  the kernel themselves always run the file they are given. `update
  install` still installs, and says the update starts when Sonar boots
  from its disk (`make run-uefi ESP_SYSTEM=1`, Keelson).
- **A persistent system partition.** When the system disk is
  `sonar/system.img` on the EFI partition (copied to RAM at boot), an
  installed kernel would be lost, so `update install` refuses.
- **Attempt counting needs persistent UEFI variables.** Apple's
  Virtualization framework (Keelson) and real machines keep them; QEMU
  with `-bios` does not (use a pflash variable store, as `make
  test-update` does). Without them the fallback to the built-in kernel
  works only for updates that fail verification or return to the
  firmware.
- **"Started" means the file system and network came up**, not that
  everything works. A kernel that boots but misbehaves later is fixed
  with `update rollback` or `update clear`, or a newer release.

## Testing

- `make test-crypto`: the crypto against OpenSSL's results (vectors in
  `tests/host/crypto_vectors.h`, from `tools/gen_crypto_vectors.py`) and
  RFC test vectors, plus tampering checks.
- `make test-update`: the whole path in QEMU with UEFI (edk2, variables in
  pflash). It builds kernels 0.1.0, 0.1.1 and 0.1.2 (one that never
  finishes starting) signed with a throwaway key, serves them from
  `tools/update_server.py` (a stand-in for GitHub's release API over TLS
  1.3, redirects included) and checks: a bad signature and a tampered
  image are rejected; a private repository gets the message above and a
  token works; a plain-HTTP mirror works; an install boots the new kernel,
  which confirms itself; the failing kernel is tried 3 times and then the
  built-in kernel takes over; rollback; a `/boot/kernel` tampered with on
  disk is refused by the loader.

`tools/update_server.py` also works for updating devices from a local
machine while the repository is private: put a release made by
`tools/release.sh` in `ROOT/pronzzz/sonar/` and set `update.api` (HTTPS,
with `--tls`) or `update.mirror` (`http://HOST:PORT/mirror/pronzzz/sonar`)
on the device.
